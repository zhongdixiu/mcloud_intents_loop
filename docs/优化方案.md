# mcloud_intents_loop 项目优化方案

> 基于版本：`2.0.1`  
> 优化前提：保留“两阶 LLM 语义召回 + Evaluator 受限重排”的核心架构  
> 本方案暂不引入：规则召回、词法召回、Embedding 召回等额外候选路径

---

## 1. 项目现状

当前系统采用两级 LLM 意图决策：

```text
用户请求
    ↓
Contextualizer
    ↓
一级 Skill Candidate Generator
    ↓
二级 Intent Candidate Generator
    ↓
Evaluator
    ↓
Switch Gate
    ↓
RouteResult
```

业务意图通过 Skill 模式提供：

- 每个 `Skill.md` 对应一个一级业务大类；
- Skill Frontmatter 和摘要用于一级 Skill 召回；
- `Tools Schema` 定义 Skill 内的二级子意图；
- 一级召回 Skill 后，二级加载对应 Skill.md 判断具体 Intent；
- Evaluator 只能在已有候选中选择，或要求定向扩充候选。

该架构的主要优点：

1. 能理解复杂自然语言和长尾表达；
2. 能处理问答、资源搜索、工具入口和内容处理之间的语义差异；
3. 一级和二级职责清晰；
4. Skill 可以独立维护子意图规则；
5. Evaluator 被限制在候选集内，降低自由生成非法标签的风险；
6. 支持多轮上下文归一和候选扩充。

本次优化不替换两阶 LLM 架构，而是重点解决当前实现中的性能、稳定性、耦合和评测问题。

---

## 2. 当前主要问题

### 2.1 二级 Intent 调用串行执行

一级默认召回多个 Skill，二级按 Skill 逐一调用模型。

典型无历史请求：

```text
一级 Skill 召回：1 次
三个 Skill 的二级 Intent 召回：3 次
Evaluator：1 次
合计：约 5 次模型调用
```

二级串行等待会显著增加总体延迟。

### 2.2 Intent 选择与参数抽取耦合

当前二级 Intent Candidate 同时输出：

- Skill；
- Intent；
- code；
- params；
- confidence；
- risk flags。

二级模型同时承担分类和信息抽取两个任务，并为多个最终不会被选中的候选重复抽取参数。

### 2.3 Evaluator 每次必经

即使是“打开回收站”“进入保险箱”等高确定性请求，也执行 Evaluator，增加延迟和成本。

### 2.4 Contextualizer 权威过强

当前 `semantic_frame.expected_result_type` 被下游视为权威诉求类型，Evaluator 不允许推翻。

一旦 Contextualizer 把工具入口误判为普通问答，错误可能贯穿整个路由链路。

### 2.5 Evaluator 与候选生成模型可能同源

未单独配置 evaluator client 时，Evaluator 默认复用主模型。

一级、二级和 Evaluator 可能产生高度相关的错误，Evaluator 不一定具备真正独立纠错能力。

### 2.6 Switch Gate 逻辑不完全符合设计目标

当前切换判断中，当最终候选就是 Evaluator 选中的候选时，可能直接允许切换，margin 门槛未真正约束普通 Evaluator 切换。

### 2.7 缺少可靠的拒识状态

系统类型支持 `matched`、`clarify`、`no_match` 等状态，但正常路由流程倾向始终输出 matched。

对于候选不足、无法安全区分和系统未支持请求，缺少清晰的：

- abstain；
- unsupported；
- error。

### 2.8 参数缺少严格本地校验

当前主要验证：

- Skill 是否存在；
- Intent 是否存在；
- code 是否匹配；
- Evaluator 是否选择合法 candidate_id。

但对 params 的字段名、类型、枚举和必填约束校验不足。

### 2.9 Skill.md 内容缺少统一结构

当前二级 Prompt 直接加载完整 `raw_markdown`。

随着 Skill 增长，可能出现：

- 路由规则与执行说明混杂；
- Prompt Token 增加；
- 无关内容干扰 Intent 判断；
- 不同 Skill 文档结构差异大；
- 参数枚举依赖自然语言解析；
- 高混淆 Intent 缺少明确对比规则。

### 2.10 候选、置信度和最终结果语义不一致

候选 confidence、Evaluator score、组合分数和最终 RouteResult confidence 的含义没有完全统一。

最终输出的 confidence 可能只是候选生成阶段的模型自报置信度，不能真实反映最终决策可靠性。

### 2.11 缺少模型调用治理

模型客户端缺少统一的：

- 请求超时；
- 重试和退避；
- 限流；
- 熔断；
- 调用预算；
- 降级策略。

### 2.12 多用户会话能力不足

对话状态主要保存在进程内对象中，不适合多进程、多实例和大规模多用户并发。

### 2.13 评测口径存在偏差风险

若只按 code 判断正确性，会掩盖：

- Skill 选错；
- Intent 选错；
- 多个 Intent 共享同一 code；
- 跨 Skill code 冲突。

必须以完整 Route Key 为主：

```text
(skill_id, intent, code)
```

---

## 3. 优化目标

1. 保留两阶 LLM 的复杂语义理解能力；
2. 降低平均延迟和不必要模型调用；
3. 解耦路由判断与参数抽取；
4. 降低 Contextualizer 错误向下传播；
5. 提升 Evaluator 的实际纠错价值；
6. 增加拒识、未支持和错误状态；
7. 完善 Candidate、Route 和 Params 的本地校验；
8. 规范 Skill.md 内容和分阶段加载；
9. 建立完整 Route Key 评测体系；
10. 为多用户、多实例和生产部署做好准备。

---

## 4. 优化后总体架构

```text
用户请求
    ↓
Contextualizer
    ↓
一级 Skill Candidate Generator
    ↓
动态 Skill 候选控制
    ↓
二级 Intent Candidate Generator
    ├── 多 Skill 并行
    ├── 只生成 Route Candidate
    └── 不抽取最终 params
    ↓
Candidate Validation
    ↓
Candidate Aggregation
    ↓
Decision Gate
    ├── 高置信、低风险、Margin 足够
    │       ↓
    │    直接选择
    │
    └── 低置信、跨 Skill 冲突、上下文不确定
            ↓
        Evaluator
            ├── select
            ├── expand
            ├── abstain
            └── unsupported
    ↓
Route Gate
    ↓
最终 Route Key
    ↓
Parameter Extractor
    ↓
Parameter Schema Validator
    ↓
执行条件判断
    ├── execute
    ├── clarify
    ├── unsupported
    └── error
    ↓
Skill 执行
```

## 5. Contextualizer 优化

### 5.1 保留职责

Contextualizer 继续负责：

- 多轮指代消解；
- 当前轮与历史关系判断；
- 省略信息补全；
- 当前轮语义归一；
- 输出 `resolved_query`；
- 输出 `semantic_frame`。

### 5.2 降低 expected_result_type 的绝对权威

当前：

```text
expected_result_type = 下游不可推翻的权威结论
```

调整为：

```text
expected_result_type = 强语义特征，但不是不可推翻的事实
```

下游优先级：

```text
当前用户显式表达
    >
候选与完整请求的语义匹配
    >
Contextualizer 的语义判断
    >
历史继承信息
```

### 5.3 增加冲突输出

建议：

```python
class ContextualizedRequest:
    resolved_query: str
    relation_to_history: str
    semantic_frame: SemanticFrame
    confidence: float
    uncertainty_notes: list[str]
    conflict_flags: list[str]
```

可识别：

- 当前轮与历史冲突；
- action 与 expected_result_type 冲突；
- 对象类型不明确；
- 默认继承策略；
- 多个合理解释。

### 5.4 下游纠错

一级、二级和 Evaluator 应允许在当前用户显式动作与 semantic frame 冲突时标记：

```text
semantic_frame_conflict
```

Evaluator 可以基于原始 query 修正路由方向，并在 diagnostics 中记录原因。

## 6. 一级 Skill Candidate Generator 优化

### 6.1 保留 LLM 一级语义召回

一级继续读取所有 Skill 的轻量摘要，并输出 Top-N Skill 候选，不改为关键词或规则系统。

### 6.2 SkillCard 规范化

一级只读取：

```python
class SkillCard:
    id: str
    name: str
    description: str
    scope: list[str]
    out_of_scope: list[str]
    version: str
```

不向一级加载：

- Tools Schema；
- 二级参数；
- 执行接口；
- 大量示例；
- API 错误码。

### 6.3 动态 Top-N

不建议完全依赖模型自报 confidence 决定是否重新调用一级模型。推荐一级一次输出最多 `max_top_skills` 个有序候选，再由本地策略选择实际进入二级的候选数量。

```text
max_top_skills = 5
默认进入二级 = 3
高置信且 Top1/Top2 分差明显 = 2
低置信或分差较小 = 4~5
```

避免为了动态 Top-N 再调用一次一级模型。

### 6.4 一级输出规范

```python
class SkillCandidate:
    candidate_id: str
    skill_id: str | None
    confidence: float
    matched_evidence: list[str]
    risk_flags: list[str]
    reason: str
```

`matched_evidence` 只允许引用当前 query、resolved_query 和 semantic frame 中真实存在的证据。

### 6.5 一级本地合法性校验

检查：

- Skill 是否存在；
- candidate_id 是否唯一；
- Skill 是否 active；
- confidence 是否在 `[0,1]`；
- ordinary dialogue 候选是否按约定表示；
- 候选数是否超过上限；
- 不允许模型输出未知 Skill。

## 7. 二级 Intent Candidate Generator 优化

### 7.1 保留按 Skill 加载完整二级路由上下文

一级选中 Skill 后，二级继续加载该 Skill 的：

```text
Skill Scope
Intent Routing Principles
Intent Contrast Rules
Tools Schema
Intent-Specific Rules
Positive Examples
Negative Examples
```

这是当前 Skill 模式的核心设计，应保留。

### 7.2 不再无差别注入完整 raw_markdown

Loader 按章节构建：

```python
class IntentRoutingContext:
    skill_id: str
    skill_name: str
    skill_scope: str
    routing_principles: str
    contrast_rules: str
    intents: dict[str, IntentSchema]
    intent_specific_rules: str
    positive_examples: str
    negative_examples: str
```

不向二级加载与路由无关的执行说明。

### 7.3 二级只判断 Route

二级输出：

```python
class IntentCandidate:
    candidate_id: str
    skill_id: str
    skill_name: str
    intent: str
    code: str
    confidence: float
    matched_evidence: list[str]
    risk_flags: list[str]
    reason: str
    alternatives: list[str]
```

从二级候选中移除最终 params。

### 7.4 参数缺失不影响 Intent 候选

二级 Prompt 明确：

- 缺联系人、时间、文件句柄和唯一对象，不影响 Route 判断；
- 当前 Skill 不支持请求时，允许返回空候选；
- 同 code 不同 Intent 仍按完整 Route Key 区分；
- 专用 Intent 优先于通用 Intent；
- 高混淆 Intent 必须参考 Contrast Rules。

### 7.5 多 Skill 二级并行

将串行：

```python
for skill in selected_skills:
    await generate_intents(skill)
```

改为受控并行：

```python
results = await asyncio.gather(
    *[
        generate_intents(skill)
        for skill in selected_skills
    ],
    return_exceptions=True,
)
```

生产实现配置并发上限：

```text
intent_generation_concurrency = 3
```

使用 `asyncio.Semaphore` 防止一次请求或大量并发请求压垮模型服务。

### 7.6 独立超时和失败隔离

每个 Skill 的二级调用应：

- 有单调用超时；
- 失败不影响其他 Skill；
- 记录失败 Skill；
- 若仍有有效候选，继续决策；
- 全部失败时进入 error 或降级路径。

## 8. Candidate Validation 和聚合

### 8.1 Route 合法性

每个 Intent Candidate 必须检查：

```text
skill_id 存在
intent 存在于对应 Skill
code 与 Tools Schema 完全一致
```

### 8.2 Route Key 去重

唯一键：

```text
(skill_id, intent, code)
```

不得按 code 单独去重。

### 8.3 候选 ID

建议稳定格式：

```text
{skill_id}:{intent}
```

同一 Route 需要保留不同证据来源时，可在内部增加来源 ID，但最终去重仍按 Route Key。

### 8.4 候选合并

同一 Route 出现多次时：

- 保留最高有效置信度；
- 合并 matched evidence；
- 合并 risk flags；
- 合并 alternatives；
- 保留来源记录；
- 避免替换对象后仍向旧对象写入 alternatives。

### 8.5 候选集保障

候选集应保留：

- 有效业务候选；
- ordinary dialogue 候选；
- Skill 级失败信息；
- 候选生成阶段 diagnostics。

## 9. Decision Gate

### 9.1 作用

Decision Gate 判断：

- 是否可以直接采用 Top1；
- 是否需要调用 Evaluator；
- 是否候选不足；
- 是否存在必须阻断的风险。

### 9.2 不直接信任模型 confidence

模型自报 confidence 未经过校准，不能直接使用固定 `0.85` 作为唯一条件。

Gate 应结合：

- Top1 与 Top2 的排序差异；
- 是否跨 Skill；
- 是否存在风险标志；
- Contextualizer 是否不确定；
- 一级与二级是否一致；
- 候选证据是否完整；
- 离线校准后的置信阈值。

### 9.3 触发 Evaluator 的条件

满足任一条件时调用 Evaluator：

1. Top1 与 Top2 来自不同 Skill；
2. Top1 与 Top2 为高混淆 Intent；
3. 候选分差低于校准阈值；
4. 存在 `label_conflict`；
5. 存在 `answer_vs_resource`；
6. 存在 `search_vs_tool_entry`；
7. 存在 `semantic_frame_conflict`；
8. Contextualizer relation 为 ambiguous；
9. 候选整体置信度低；
10. 一级和二级 evidence 明显不一致；
11. 候选中没有明确合理结果。

### 9.4 可直接选择的条件

同时满足：

- Top1 Route 合法；
- Top1 与 Top2 差异达到校准要求；
- 不存在跨 Skill 高风险冲突；
- Contextualizer 无关键不确定性；
- 当前 query 有明确证据；
- 无阻断风险。

阈值必须通过离线数据校准，不凭经验固定。

## 10. Evaluator 优化

### 10.1 从必经节点改为条件节点

简单、高确定性请求不调用 Evaluator。

Evaluator 专注处理：

- 跨 Skill 冲突；
- 普通问答与业务请求冲突；
- 搜索与工具入口冲突；
- 专用 Intent 与通用 Intent 冲突；
- 低 margin；
- 候选召回缺口；
- 上下文语义冲突。

### 10.2 输出状态扩展

```python
class RerankDecision:
    verdict: Literal[
        "select",
        "expand",
        "abstain",
        "unsupported",
    ]
    selected_candidate_id: str | None
    confidence: float
    ranking: list[CandidateScore]
    reason: str
    expand_scope: str | None
    expansion_hint: str | None
    risk_flags: list[str]
```

| verdict | 含义 |
|---|---|
| `select` | 候选集中存在明确合理结果 |
| `expand` | 正确方向可能存在，但候选集漏召回 |
| `abstain` | 存在多个合理候选，当前证据不足 |
| `unsupported` | 当前 Skill 集不支持该请求 |

### 10.3 Evaluator 独立性

优先方案：

- 使用独立 Evaluator 模型配置；
- 使用更低温度；
- 使用与候选生成不同的 Prompt；
- 不把候选生成模型的长篇 reason 当成事实；
- 重点读取 query、Route 定义和真实 evidence。

若仍复用同一模型，应至少使用不同系统 Prompt 和独立调用参数。

### 10.4 Evaluator 约束

Evaluator 必须：

- 只能选择已有 candidate_id；
- 不能重写 Skill、Intent 或 code；
- 不能因参数缺失降低候选；
- 可以指出 Contextualizer 冲突；
- expand 必须给出明确 scope；
- abstain 必须说明缺少的判别信息；
- unsupported 必须说明候选为何均不匹配。

### 10.5 Expansion 控制

保留定向扩充，限制：

```text
max_expansion_rounds = 1
```

扩充后：

- 只访问未覆盖 Skill 或目标 Skill；
- 不重复已有 Route；
- 再执行一次 Candidate Validation；
- 再进入 Decision Gate 或 Evaluator；
- 超过轮次后不得无限循环。

## 11. Route Gate 和 Switch Gate 优化

### 11.1 统一最终决策逻辑

最终选择必须来自合法候选集。

Gate 输入：

- 首次 Top1；
- Evaluator 选择；
- Candidate scores；
- risk flags；
- Contextualizer 冲突；
- expansion 状态。

### 11.2 修正切换逻辑

不得因为“final candidate 等于 Evaluator selected”就自动绕过 margin。

推荐逻辑：

```python
switch_allowed = (
    selected_is_valid
    and evaluator_confidence >= evaluator_threshold
    and score_margin >= switch_margin_threshold
    and not blocking_conflict
)
```

若产品定义 Evaluator 是低置信场景的最终裁判，也可简化为：

```text
Evaluator 满足合法性和置信要求后直接选择
```

二者必须二选一，避免同时保留“Evaluator 最终裁判”和“形式化但失效的 margin gate”。

### 11.3 风险分级

建议区分：

```text
blocking:
- illegal_route
- label_conflict
- semantic_frame_severe_conflict

non_blocking:
- answer_vs_resource
- search_vs_tool_entry
- context_unclear
```

具体分级基于评测调整。

### 11.4 最终状态

```python
class RouteDecision:
    status: Literal[
        "matched",
        "abstain",
        "unsupported",
        "error",
    ]
    selected_candidate_id: str | None
    confidence: float
    diagnostics: RouteDiagnostics
```

## 12. Parameter Extractor 后置

### 12.1 新流程

```text
最终 Route Key
    ↓
读取唯一 Intent 的参数 Schema
    ↓
Parameter Extractor
    ↓
Parameter Validator
    ↓
执行条件判断
```

### 12.2 优势

- 只抽取一次；
- 分类任务和参数抽取任务解耦；
- 减少 Prompt 复杂度；
- 避免多个候选产生不一致参数；
- 更容易单独评测参数准确率；
- 参数错误不会影响候选召回排序。

### 12.3 参数抽取输出

```python
class ParameterExtractionResult:
    params: dict[str, Any]
    missing_required: list[str]
    uncertain_fields: list[str]
    evidence: dict[str, list[str]]
```

### 12.4 本地参数校验

必须校验：

- 字段是否在 Schema 中；
- 类型是否合法；
- 枚举是否合法；
- 数组元素是否合法；
- 必填参数是否缺失；
- 是否出现禁止的附加字段；
- 是否伪造 file_id、image_id、mail_id 等真实句柄。

### 12.5 澄清与执行分离

参数缺失时：

- Intent 已确定；
- RouteResult 不重新变成其他 Intent；
- 根据参数 Schema 决定是否澄清；
- 可选参数缺失不阻塞；
- 必填且无法从上下文获取时输出 clarify；
- 高风险操作需要用户确认。

## 13. Skill.md 规范化和加载优化

详细要求见《skill规范化要求.md》。

### 13.1 保留当前语义层级

```text
一个 Skill.md = 一个一级意图大类
Tools Schema = 该 Skill 内的二级子意图
```

### 13.2 一级轻量加载

一级只加载：

- Skill ID；
- 名称；
- 描述；
- scope；
- out_of_scope；
- version。

### 13.3 二级按需加载

一级命中后，二级加载：

- Skill Scope；
- Intent Routing Principles；
- Intent Contrast Rules；
- Tools Schema；
- Intent-Specific Rules；
- Positive/Negative Examples。

### 13.4 执行说明延后加载

最终 Route 确定后才加载：

- 参数转换；
- API 说明；
- 权限；
- 用户确认；
- 异常处理；
- 返回结构。

### 13.5 不强制立即拆文件

第一阶段优先统一单个 Skill.md 的章节结构。

只有 Skill 明显膨胀后才拆为：

```text
SKILL.md
ROUTING.md
EXECUTION.md
```

Tools Schema 和二级规则必须一起进入 ROUTING 上下文。

## 14. 模型调用可靠性治理

### 14.1 超时

为不同阶段设置独立超时：

```text
contextualizer_timeout
skill_router_timeout
intent_router_timeout
evaluator_timeout
parameter_extractor_timeout
```

### 14.2 重试

仅对以下错误重试：

- 网络超时；
- 429；
- 5xx；
- 短暂连接失败；
- 可恢复的结构化输出失败。

推荐：

```text
max_retries = 2
exponential_backoff + jitter
```

### 14.3 总请求预算

单次 route 设置总 deadline，避免各阶段重试叠加导致超时。

```text
route_deadline_ms
```

每个阶段根据剩余预算决定是否继续扩充或调用 Evaluator。

### 14.4 并发限制

需要：

- 全局模型并发限制；
- 单请求二级并发限制；
- 单用户并发限制；
- 模型服务限流；
- 排队超时。

### 14.5 熔断和降级

Evaluator 服务不可用时：

- Decision Gate 已有高可靠 Top1，可按本地 Gate 输出；
- 否则输出 abstain 或 error；
- 不悄悄将任意候选标为高置信 matched。

## 15. 会话和多用户优化

### 15.1 会话隔离

会话 Key 至少包含：

```text
tenant_id
user_id
session_id
```

### 15.2 外部状态存储

生产环境不依赖进程内 Python 对象保存历史。

```python
class SessionStore:
    async def load(session_key) -> DialogueHistory: ...
    async def save(session_key, history) -> None: ...
```

可选实现：

- Redis；
- 数据库；
- AgentScope 已有持久化状态能力；
- 其他统一 Session 服务。

### 15.3 历史治理

- 限制历史轮数；
- 记录最终 Route 和关键语义状态；
- 对敏感参数脱敏；
- 历史中的错误 Route 不被无条件继承；
- 当前轮显式表达始终优先。

## 16. 置信度和可解释性优化

### 16.1 区分不同分数

不要混用：

- 一级 Skill confidence；
- 二级 Intent confidence；
- Evaluator score；
- 最终 Route confidence。

Diagnostics 保留所有原始分数，最终 confidence 单独计算。

### 16.2 最终 confidence

最终置信度可基于：

```text
一级候选强度
+ 二级候选强度
+ Top1/Top2 margin
+ Evaluator 是否确认
- 风险惩罚
- Contextualizer 不确定性
```

具体权重通过验证集校准。

### 16.3 不直接将 LLM 自报分数视为概率

LLM confidence 只作为特征，不作为真实概率。

可使用：

- 分桶校准；
- Platt scaling；
- Isotonic regression；
- 业务阈值校准。

### 16.4 Diagnostics

建议记录：

- resolved query；
- context relation；
- 一级候选；
- 二级候选；
- 校验丢弃原因；
- 是否调用 Evaluator；
- Evaluator 选择和排序；
- 是否发生扩充；
- Gate 结果；
- 参数校验结果；
- 模型调用次数；
- 各阶段耗时。

## 17. 评测体系优化

### 17.1 核心标签

测试集应包含：

```text
expected_skill_id
expected_intent
expected_code
expected_params
alternate_routes
```

主标签：

```text
RouteKey = (skill_id, intent, code)
```

### 17.2 一级指标

- Skill Recall@1；
- Skill Recall@3；
- Skill Recall@5；
- ordinary dialogue 召回率；
- 一级错误分布。

### 17.3 二级指标

- Intent Recall@1；
- Intent Recall@2；
- 正确 Skill 内 Intent Accuracy；
- 高混淆 Intent 对准确率；
- 空候选正确率。

### 17.4 候选集指标

- Full Route Recall@K；
- Candidate Set Coverage；
- 正确 Route 首位率；
- expansion 前后 recall 增益。

### 17.5 最终指标

- Full Route Accuracy；
- Skill Accuracy；
- Intent Accuracy；
- Code Compatibility Accuracy；
- abstain precision；
- unsupported precision；
- clarify precision。

### 17.6 Evaluator 指标

- Evaluator 调用率；
- Evaluator switch count；
- Evaluator switch gain；
- Evaluator switch loss；
- Wrong Switch Rate；
- Expansion Gain；
- Expansion Waste Rate；
- Unnecessary Evaluator Call Rate。

### 17.7 参数指标

- 参数字段 Precision；
- 参数字段 Recall；
- 参数 Exact Match；
- 枚举合法率；
- 必填参数识别率；
- 虚构句柄率。

### 17.8 性能指标

- 平均模型调用次数；
- P50/P95/P99 延迟；
- 各节点 Token 消耗；
- 二级并行度；
- 超时率；
- 重试率；
- 错误率。

### 17.9 评测模式

明确区分：

- `gold_history`：使用标准历史，主要评估当前轮；
- `end2end`：从第一轮开始真实执行，评估错误传播；
- `no_evaluator`：评估 Evaluator 净收益；
- `conditional_evaluator`：评估 Gate 策略。

生产准确率以 end-to-end Route Key 指标为主。

## 20. 分阶段实施计划

### 阶段一：正确性修复

任务：

1. 评测主指标改为完整 Route Key；
2. 修复 Candidate 去重和 alternatives 合并；
3. 修正 Switch Gate；
4. 增加 `abstain`、`unsupported`、`error`；
5. 参数增加本地 Schema 校验；
6. Contextualizer 结果允许下游冲突修正；
7. 明确最终 confidence 含义。

验收：

- Full Route Accuracy 可稳定统计；
- 错误切换率可观测；
- 不支持请求不再强制 matched；
- 非法 params 被本地拦截。

### 阶段二：链路解耦和性能优化

任务：

1. 二级 Intent 并行化；
2. 二级候选移除 params；
3. 新增 Parameter Extractor；
4. Evaluator 改为条件触发；
5. 增加独立超时、重试和总 deadline；
6. 增加模型并发限制。

验收：

- 平均模型调用次数下降；
- P95 延迟下降；
- 参数准确率单独可测；
- Evaluator 净收益为正。

### 阶段三：Skill 规范化

任务：

1. 统一 Skill.md Frontmatter；
2. 增加 scope/out_of_scope；
3. 增加 Intent Routing Principles；
4. 增加 Intent Contrast Rules；
5. 统一 Tools Schema 参数格式；
6. Loader 按章节加载；
7. 增加 Skill 静态校验。

验收：

- 新增 Skill 无需修改中心 Router；
- 一级不读取完整 Skill.md；
- 二级不读取无关执行说明；
- Skill 错误可在启动或 CI 阶段发现。

### 阶段四：生产化

任务：

1. SessionStore 外部化；
2. 多用户和多租户隔离；
3. Skill 版本和热更新；
4. 指标、日志和链路追踪；
5. PII 脱敏；
6. 灰度、回滚和版本对比；
7. 在线混淆矩阵和错误样本回流。

验收：

- 多实例部署时会话一致；
- Skill 可安全热更新和回滚；
- 线上错误可定位到具体节点和 Skill 版本；
- 关键指标可持续监控。

## 21. 风险与应对

### 21.1 二级并行导致模型服务压力增加

应对：

- 使用 Semaphore；
- 设置全局并发；
- 限制实际进入二级的 Skill 数；
- 单 Skill 失败隔离。

### 21.2 Evaluator 条件化后可能漏掉纠错机会

应对：

- 先通过离线数据设计 Gate；
- 灰度期间同时运行 Evaluator 但不影响结果；
- 统计“跳过 Evaluator 时，Evaluator 是否会改判”；
- 逐步放开直接选择比例。

### 21.3 参数后置增加一次模型调用

当前二级已经为多个候选抽参数。后置后虽然形式上增加独立节点，但通常只对一个最终 Route 调用，整体 Token 和任务复杂度更低。

可根据 Intent 复杂度：

- 简单参数本地解析；
- 复杂参数调用 LLM；
- 无参数 Intent 跳过 Parameter Extractor。

### 21.4 Contextualizer 不再绝对权威可能增加下游分歧

应对：

- 当前轮显式证据优先；
- 仅在明确冲突时允许修正；
- 记录 semantic frame conflict；
- 在评测中单独统计纠错收益和错误推翻率。

### 21.5 Skill 规范化工作量较大

应对：

- 先改高频和高混淆 Skill；
- 提供 Skill 模板；
- 编写静态检查工具；
- 支持旧格式兼容期；
- 分批迁移。

## 22. 最终推荐架构

```text
Contextualizer
    │
    │ 输出 resolved_query 和可修正 semantic_frame
    ▼

    │
    │ 读取轻量 SkillCard
    ▼

    ▼

    ▼

    ▼

    ├── 高可靠候选直接选择

    ▼

    ▼

    ▼

    ▼

    ▼

    ▼

```

## 23. 结论

当前项目“两阶 LLM 语义召回 + Evaluator 重排”的架构方向合理，应继续保留。

优化重点不是将系统改造成规则或检索路由，而是：

- 保留一级 Skill 和二级 Intent 的语义分层；
- 保留一级命中后按需加载 Skill.md 的机制；
- 规范 Skill 内部路由信息；
- 二级调用并行化；
- 路由和参数抽取解耦；
- Evaluator 条件化；
- Contextualizer 允许被证据纠正；
- 修正 Gate 和拒识机制；
- 使用完整 Route Key 评测；
- 增加本地 Schema 校验和生产治理。

> 最终形成一个以 Skill 为业务扩展单元、以两阶 LLM 为核心语义决策能力、以本地校验和条件 Evaluator 保证稳定性、以独立参数抽取和执行层保证可维护性的意图识别系统。
